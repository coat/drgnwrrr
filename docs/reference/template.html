Porting rules

  1. One RNG, passed by pointer. Every random roll in the game comes from one 16-bit state at $94/$95. Don't use std.Random. The number and order of calls is part of the game's behavior, so keep it identical and pin sequences in tests.
  2. Some code re-reads the last value. The step routine calls the RNG once, then several checks read $95 again without calling. Use rng.hi() for those reads, not rng.next().
  3. Every controller read advances the RNG. The joypad routine $C608 starts with JSR $C55B, and the input-wait loops ($CBCD, $CFE4, $CA9F) call it once per frame (NTSC ≈ 60.0988 Hz, 16.64 ms). Plain frame waits ($FF74) don't. In towns, NPC movement (bank 0 $B7A1) and some dialogue ($D154, $D468) also call the RNG. Give the engine an idleFrames() that frontends call while waiting for input. A CLI can convert elapsed time to frames. Tests can pass a fixed count.
  4. Stay in u8. Use +%/-% where the 6502 wraps. Widen to u16 only where the game uses a byte pair ($3C3D, $4041…). Safe builds panic on any overflow you didn't intend, which catches port mistakes.
  5. Model the carry when a branch reads it. @addWithOverflow returns .{ result, carry }, which matches ADC then BCS.

A Common algorithms

Three subroutines that everything else calls: the RNG, a 16×16 multiply, and a 16÷8 divide.

Random number generator

ROM ✓$C55Bis the callL1119

A 16-bit linear congruential generator. $94 is the low byte and $95 the high byte. Every routine uses $95 as RAND (0–255).

state = state × 0x303 + 0x81 (mod 0x10000) RAND = state >> 8

The routine does ×3 (shift and add), then $95 += $94 (which is ×257 mod 2¹⁶), then +0x81. 3 × 257 = 771 = 0x303.

QUIRKThe multiplier 771 fails the Hull–Dobell condition for full period (771 − 1 isn't divisible by 4). The 65,536 states split into two separate cycles of 32,768. Low byte mod 4 is always in {0, 1} on one cycle and {2, 3} on the other. Your seed picks the cycle for the whole game.
QUIRKConsecutive outputs are strongly patterned. Over all 65,536 states, the longest run of even RAND values is 8 when every call is sampled, but only 5 when every 4th call is sampled. The hero's wake roll is every 4th call, which is why sleep can't last. Try different strides in the RNG lab.
QUIRKThe last ADC #$00 leaves the carry flag set when the 16-bit add overflows. The run routine at $EEBB does ADC without CLC, so that carry gets added. The Zig port keeps the carry as rng.carry.

Multiply

$C1C9L1197
$4041 = $3C3D × $3E3F (16-bit, truncated)

Most call sites multiply two bytes and then read only $41, the high byte. That's (a × b) >> 8, the game's way of scaling a value by RAND/256.

Divide

$C1F0L1228
$3C = $3C3D / $3E remainder in $40

Entry at $C1F0 clears $3D first (8-bit dividend). Entry at $C1F4 keeps it (16-bit dividend, used by the name/stat code). In Zig this is plain integer / and %. Mind which width you divide in.

Radiant & Torch

ROM ✓$DA6A$CA5AL1293

The light radius byte $D0 shows ($D0 − 1) / 2 extra tiles. RADIANT sets it to 7 with an 80-step timer ($DA = 0x50). Each time the timer hits 0, the radius drops by 2 and the timer resets to 60 (0x3C).

3 tiles × 80 steps → 2 tiles × 60 → 1 tile × 60 → dark (200 total)

A Torch sets $D0 = 3 (1 tile) and lasts until you leave the dungeon.

ROMThe guide skips the guard at $CA56: the step code does nothing while the timer is 0. A torch leaves the timer at 0, so it never fades. RADIANT's last stage counts down to 0 at radius 1 and then stops.

REPEL & Fairy Water

ROM ✓$DA98$CF20L1323

Sets $DB to 0xFF (REPEL) or 0xFE (Fairy Water). It drops by 2 per step and wears off when it reaches 1 (REPEL) or 0 (Fairy Water), so both last 127 steps. Which value it stops on picks the wear-off message. It works on the overworld only, and the check runs after the enemy has been chosen.

half = DEF >> 1 repelled = STR < half or (STR >> 1) ≥ STR − half

That's roughly "repelled when your defense ≥ the enemy's strength".

ERRATAThe guide's summary DEF>>1 > STR>>1 disagrees with its own opcodes for 256 (DEF, STR) pairs. Its example (DEF 51 vs STR 50, "won't evade") is repelled by the code. Port the opcodes.

Overworld zones

ROM ✓$CE7C$F522+1 in zone 0L1541

The 120×120 overworld is an 8×8 grid of 15×15-tile cells. Each cell has a zone number, stored two per byte in 32 bytes at $F522. An even grid x uses the high nibble, an odd one the low nibble.

gx = x / 15, gy = y / 15 byte = $F522[gy*4 + (gx >> 1)] zone = gx odd ? byte & 0x0F : byte >> 4

Zone 0 (around Tantegel) makes one more RNG call and needs RAND & 3 == 0 on hills or RAND & 1 == 0 on anything else. That halves the rate (quarters it on hills).

Other maps ($CED8): map 2 → zone 16, map 3 (Hauksness) → 13, map 6 → 18. Maps 0x0F–0x1B read $F542 when $16 = 0x20, which is always true there: $16 is the map type, 0x20 for every map from 0x0F up. Every other map has no random encounters.

ROMThe guide's §II zone grid is wrong in three cells. The ROM table at $F522 gives grid (4,2) = 2 (guide: 1), (4,3) = 6 (guide: 9) and (4,4) = 9 (guide: 12). The map and Zig below use the ROM values.

One step, end to end

ROM ✓$CBF7$CCF6$CDA21 call (+ encounter)composite

After a move (see moving, stairs and warps), bank 0 $B219 checks the map bounds. Stepping off the edge of a town or castle takes the first warp-table entry for that map ($B228) and skips everything below. Otherwise $CBF7 runs, in this order:

  1. Armor regen ($CCF6), on every map: Erdrick's Armor +1 HP per step, Magic Armor +1 HP every 4th step, capped at max HP. Magic Armor's step counter $E3 only ticks while it's worn and is never reset.
  2. Cursed at Tantegel ($CD30): on map 4, row 27, a cursed hero is sent out (see items).
  3. Fixed battles ($CD51–$CD9F): Axe Knight, Green Dragon, Golem. No RNG call before the fight starts. The Axe Knight has no "beaten" flag.
  4. The step's RNG call ($CDA2), then the tile lookup. Tiles 0x07–0x09 (entrances) go to the map change at $D941 here, so stepping onto a town or cave still advances the RNG once.
  5. Swamp −2 / barrier −15 ($CDC6, $CE17), unless you wear Erdrick's Armor. HP stops at 0, and 0 HP goes straight to death ($EDA7) with no encounter check. No RNG use.
  6. Encounter: the tile mask test on that same roll, then zone, slot and REPEL (the sections above).

With $E4 bit 2 set (Dragonlord beaten), steps 1–3 are skipped, standing at Tantegel (10 or 11, 8) starts the ending, and the code returns after the entrance check, so there are no damage tiles or encounters. Back in the main loop ($CA56), the RADIANT and REPEL timers tick after every move.

QUIRKRegen comes first, so on a swamp tile with Magic Armor the heal and the damage land on the same step. A swamp step at 2 HP or less is fatal unless the regen fires first. The barrier's 15 damage is one subtraction, not three: the three-flash loop before it is only the animation.

Walking costs one more RNG call per tile. The field loop ($CA9F) reads the joypad once ($C608, which calls the RNG), and with a direction held it moves straight away: the scroll waits 16 frames (19 on hills, the three extra waits) without polling, then the step runs and the loop reads the joypad again. So holding a direction costs 2 RNG calls per tile: that read and the step's roll at $CDA2. It's the same on every terrain and in caves. The move gate ($B252: $4F & 0x0F) never makes a held direction wait, because the loop clears the frame counter $4F just before each read ($CA9B). Standing still polls once per frame, so the time a player spends between moves goes to idleFrames().

Spell resistance (hero casting)

ROM ✓$E9461 callL1820

One shared routine. The spell works when (RAND & 0x0F) ≥ resist, so it lands with chance (16 − resist)/16.

  • SLEEP: SR >> 4
  • STOPSPELL: SR & 0x0F
  • HURT / HURTMORE: DR >> 4

Enemies that cast no spells still have STOPSPELL resist 15, so it lands 1/16 of the time and does nothing.

Enemy dodge

ROM ✓$E66E1 callL1882

Chance (DR & 0x0F)/64. Excellent moves can be dodged too. The dodge roll comes after the damage roll. It's skipped, with no RNG call, when the enemy is asleep or the damage was 0.

QUIRKSTA $95 writes RAND & 0x3F back into the RNG's high byte, so the next RNG output depends on this write. Call rng.setHi() or the following rolls will drift from the original.

The treasure chest bug

ROM ✓$E209$E39A$601CL2620

A chest counts as opened if its coordinates are in an 8-slot list at $601C (x, y pairs, (0,0) = empty). The game never checks the tile you're standing on.

  • The list (and the door list before it) is cleared only when you arrive on the overworld (bank 0 $AF2B), so moving between connected maps such as castle floors or cave levels keeps it, and so does dying.
  • Entering the throne room, once you've left it at least once ($DF bit 3), puts its 3 chests into the last 3 slots (bank 0 $AF3C).
  • When the list is full, a new coordinate is silently dropped, so that chest never registers as opened.

Open 2+ chests in a dungeon, die, then loot the treasury: one chest refills forever. For a faithful clone, keep the bug.

Not saved: position (you always continue at the king), REPEL and RADIANT timers, the chest and door lists, and battle status ($DF bits 4–7 are cleared at the start of every battle).

QUIRKThe CRC is computed in $94/$95, the RNG state. Every save leaves the RNG equal to the saved record's CRC, and so does every load (power-on test loads included). So after saving at the king, or after continuing, the next random roll depends on your save data, not on anything before it. A faithful engine sets rng.state to the CRC at those points, as Sram.save and Sram.load do.
QUIRKThe load check ($FB4A) writes the freshly computed CRC into each copy before comparing it with the stored one, so even a failed copy ends up with a matching CRC. It doesn't matter in practice: a load that fails on all 10 copies erases the slot at boot.

The Dragonlord's offer & carrying the princess

ROM ✓$D4AB$D3B20 calls

The Dragonlord's offer ($D4AB) is two yes/no questions. Any "no" starts the battle with enemy 0x26 after a 40-frame pause. "Yes" twice runs $D4E7: XP, gold, items, keys, herbs, equipment and all three flag bytes are zeroed in RAM, the ending text prints, and the game hangs in an endless loop at $D530. Nothing is written to SRAM, so after a reset the last save is still there. Your engine can treat it as a game-over that leaves the save alone.

When he falls ($E99E), the victory code branches before the XP and gold at $EA0A, so neither form gives XP or gold, and there's no gold roll. Beating the first form (0x26) waits 80 frames (no RNG calls) and starts the battle with his true form (0x27) at $E4DF, the same start as a fixed battle. Beating the true form ($E9B1) clears $E0 to 0, sets $E4 bit 2, waits for a button, refills HP and MP, and puts you outside on the overworld at Charlock's gate (48, 48), the source of warp entry 6 ($EA03 → $D9E2). From there you walk or RETURN to Tantegel; the ending starts in front of the king (see one step).

Carrying the princess ($DF bit 0) changes very little. Only the hero sprite (bank 0 $B6EE), one map tile (tile 0x17 becomes brick once she's rescued, bank 0 $ACF5), a few NPC lines, the inn text and the king read it. Battles, encounters, spells (RETURN included), items and stairs don't. Dying clears the bit without setting "returned", so she counts as not rescued again. The Green Dragon stays beaten ($E4 bit 6).

Back at the king ($D3B2) you get Gwaelin's Love, and $DF goes from carrying to returned. With all 8 item slots full, the game doesn't ask you to throw anything away. It takes the first of Torch, Dragon's Scale, Fighter's Ring, Fairy Water, Wings, Cursed Belt, Staff of Rain that you have ($D54C) and puts the Love there. If you have none of those, you get no Love at all, but she still counts as returned.

QUIRKThe king's swap list includes the Cursed Belt even while it's worn. It's removed, but $CF bit 6 stays set, so you stay cursed with no belt until the curse is lifted. It also includes the Staff of Rain, a quest item the throw-away prompt protects.

G Maps & movement

How the game reads its 29 maps, which tiles you can walk on, and how entrances, stairs and map edges move you between maps. Everything a pathfinder needs, read from the ROM. The guide doesn't cover any of it.

Map data and the tile lookup

ROM ✓$801A$AC17$99F0

Every map is numbered by $45. Loading one copies its 5-byte row from bank 0 $801A + map × 5 to $11–$15: a data pointer, the largest x and y, and the tile that lies past the edge. Each tile is then looked up on demand by bank 0 $AC17, with x in $3C and y in $3E. The result comes back in $3C, and the step code keeps it in $E0.

  • Overworld (map 1): 120×120, run-length encoded. $A653 holds one pointer per row. Each byte is tile << 4 | (run − 1), and runs never cross rows. The nibble goes through $99E3. Water (nibble 4) instead picks one of 16 shore tiles by which of its four neighbours are land ($AB24). Bridges count as water there.
  • Every other map: two tiles per byte, high nibble first (even x), rows of (max_x + 1) / 2 bytes. Maps from 0x0C up keep only 3 bits. The tile is $99F0[nibble + $16], where $16 is the map type: 0x10 for towns, castles and shrines, 0x20 for maps 0x0F and up.
  • Past the edge ($AB77): x above $13 or y above $14 gives the border tile $15. On the overworld, the tiles one step outside are shore water matched to the tile inside, and anything further out is plain water.

A few tiles depend on progress. The lookup checks them every time, so a map always reflects the flags:

  • Overworld (64, 49) is a bridge once $CF bit 3 is set (Rainbow Drop). Before that, it's water.
  • Charlock (map 2) at (10, 1): the stairs behind the throne read as barrier until SEARCH sets $CF bit 2.
  • The princess tile (Swamp Cave) reads as brick once $DF bit 0 or 1 is set (carrying or returned her).
  • Chests and doors whose (x, y) are in the chest log ($601C) or door log ($600C) read as brick. Only coordinates are compared, not the map.

Moving, stairs and warps

ROM ✓$B1CC$B228$D941$D9AF

Moving (bank 0 $B1CC): the target tile is looked up, and anything at 0x0E or above blocks the move. In towns, an NPC on the target tile blocks it too. Then $B219 checks the bounds. A target past the edge on any map but the overworld takes the first warp entry whose destination is this map, and puts you at that entry's source ($B228). Otherwise the step routine runs with the new tile.

Entrances: stepping on a town, cave or castle tile (0x07–0x09, overworld only) jumps to $D941 right after the step's RNG call. It finds the first entry whose source is your (map, x, y) and moves you to its destination.

STAIRS ($D9AF): on stairs down (0x05), the same forward search as an entrance. On stairs up (0x03), the reverse: the first entry whose destination is here, back to its source. Anywhere else, or with no matching entry, you get a message and nothing changes.
